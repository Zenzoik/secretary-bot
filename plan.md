# Telegram Secretary Bot — Спецификация и план реализации

Версия: 1.1
Дата: 28.08.2026
Связанный документ: `tech-stack.md`

---

## Часть I. Идея

### Проблема

Владелец получает сообщения круглосуточно. Ночью и в выходные он не отвечает, но отправитель этого не знает: человек ждёт, нервничает, пишет повторно. Отдельная категория — сообщения про деньги: их владелец хочет видеть первыми, а отправителю важно понимать, что вопрос не потерялся.

### Решение

Бот, подключённый к личному аккаунту через Telegram Secretary Mode. В нерабочее время он отвечает от имени владельца одним коротким сообщением, а денежные вопросы дополнительно кладёт в утренний список владельца.

Получатель видит обычное сообщение от владельца — без пометки о боте. Поэтому текст должен быть честным, а бот в переписку не вступает: одно сообщение и молчание.

### Чего решение НЕ делает

- Не ведёт диалог вместо человека
- Не работает в группах (платформа не позволяет)
- Не пишет первым (окно 24 часа)
- Не заменяет владельца в решении вопросов — только снимает тревогу ожидания

## Часть II. Спецификация

### 2.1 Функциональные требования

**FR-1. Подключение**
Бот подключается к аккаунту владельца через Secretary Mode. Обрабатывает установку, изменение прав и разрыв соединения.

**FR-2. Область действия**
Политика «все чаты, кроме исключений». Новый контакт автоматически попадает под действие бота.

**FR-3. Расписание**
Владелец задаёт quiet-окна: дни недели + интервал времени + таймзона. Бот отвечает только внутри окна. Окна через полночь поддерживаются.

**FR-4. Исключения**
Контакт можно исключить навсегда или до конца дня. Жёстко исключены всегда: боты, сервисные аккаунты, сообщения самого владельца.

**FR-5. Два сценария ответа**

| Условие | Шаблон |
|---|---|
| Обычное сообщение | «Сейчас нерабочее время, отвечу позже» |
| Денежная тематика | «Отвечу первым делом утром» |

Тексты редактируются владельцем.

**FR-6. Классификация**
LLM определяет категорию сообщения. При недоступности LLM — fallback на словарь ключевых слов. При уверенности ниже порога — общий шаблон.

**FR-7. Один ответ на окно**
Сколько бы сообщений контакт ни прислал за одно quiet-окно, автоответ уходит один раз.

**FR-8. Задержка**
Ответ отправляется через 60–240 секунд после входящего (случайно).

**FR-9. Приоритет живого человека**
Если владелец ответил в чат сам до истечения задержки — автоответ отменяется.

**FR-10. Утренний список**
Денежные сообщения попадают в список, который владелец получает в 08:00: кто, во сколько, о чём одной строкой.

**FR-11. Dry run**
Режим, в котором бот ничего не отправляет контактам, а показывает владельцу предполагаемый ответ с кнопками оценки.

**FR-12. Управление**
Постоянная клавиатура в личке бота: статус, включение, выключение, пауза,
статистика за день и подтверждение live. Slash-команды остаются запасным
интерфейсом. Deep-link «Manage Bot» из любого управляемого чата открывает
карточку контакта с быстрыми действиями.

**FR-13. Лог**
Все решения бота записываются: контакт, время, действие, категория, шаблон. Без тел сообщений.

**FR-14. Закрытый доступ и onboarding**
Подключить бота может только мастер или приглашённый им пользователь. Мастер
создаёт одноразовые ограниченные по времени ссылки, видит технический список
пользователей и может немедленно отозвать доступ. Новый пользователь до начала
обработки проходит безопасный onboarding: права Telegram, область тестовых
чатов, таймзона, расписание и обязательный dry-run.

### 2.2 Нефункциональные требования

| ID | Требование |
|---|---|
| NFR-1 | Ответ на webhook Telegram — менее 200 мс, вся работа асинхронно |
| NFR-2 | Тела сообщений в MVP не сохраняются нигде |
| NFR-3 | В LLM уходит только текущее сообщение, без истории и имён |
| NFR-4 | Kill switch срабатывает в два тапа с телефона |
| NFR-5 | Ошибка LLM или БД никогда не приводит к отправке неверного сообщения — при сбое бот молчит |
| NFR-6 | Дедупликация входящих: повторная доставка апдейта не даёт второго ответа |
| NFR-7 | Схема БД мультиарендная, всё привязано к `connection_id` |
| NFR-8 | Мастер задаётся вне Telegram через окружение и не может быть назначен пользовательской командой |
| NFR-9 | Мастер управляет доступом и техническим статусом, но по умолчанию не видит контакты, превью и переписку других владельцев |

### 2.3 Принцип по умолчанию

**При любой неопределённости бот молчит.** Пропущенный автоответ — незаметен. Неуместный автоответ важному человеку в 3 часа ночи — репутационный ущерб и потеря доверия к системе.

### Этап 1.6. Автоматический onboarding и закрытый доступ

**Объём:** 1.5 дня
**Цель:** владелец проекта самостоятельно и безопасно допускает заказчиков к
пилоту без ручных SQL-настроек.

**Модель доступа**

- Единственный master bootstrap задаётся переменной
  `MASTER_TELEGRAM_USER_ID`; Telegram-команда не может создать или заменить
  мастера.
- В БД хранится allowlist владельцев со статусами `pending`, `active`,
  `revoked`, ролью, автором и временем изменения; invite-токены хранятся
  отдельно только в хешированном виде.
- Добавление выполняется одноразовой invite-ссылкой с криптографически случайным
  токеном, сроком действия и атомарным погашением. Переход по ссылке создаёт
  запрос `pending`, а мастер отдельно подтверждает конкретный Telegram `user_id`.
  Username используется только для отображения, но не для авторизации.
- Неавторизованный `business_connection` не запускает pipeline и не создаёт
  рабочие настройки. Событие записывается без тел сообщений, мастер получает
  техническое уведомление.
- Отзыв доступа немедленно включает kill switch, отменяет live-подтверждение и
  удаляет ожидающие задачи этого владельца из Redis.

**Задачи**

1. Добавить таблицы/поля ролей, allowlist, invite-токенов и состояния onboarding
2. Добавить мастер-панель Reply Keyboard: пользователи, пригласить, подтвердить
   запрос, отклонить, отозвать, технический статус
3. Реализовать одноразовый deep-link приглашения с TTL и защитой от повторного
   использования
4. Поставить проверку допуска перед созданием/обновлением Business Connection,
   командами владельца и обработкой сообщений
5. Реализовать FSM onboarding: подключение Chat Automation → проверка прав
   `can_reply`/`can_read_messages` → таймзона → расписание → подтверждение
   `Only Selected Chats` → тестовый dry-run
6. Добавить безопасные presets расписания и возможность вернуться/исправить
   предыдущий шаг до активации
7. До завершения onboarding держать `dry_run = true` и `kill_switch = true`;
   live недоступен
8. Добавить отдельные тесты изоляции двух владельцев и runbook подключения
   заказчика

**DoD**

- [ ] Пользователь без приглашения не может активировать подключение, команды
  или обработку Business Messages
- [ ] Мастер создаёт приглашение кнопкой и получает ссылку, пригодную для
  пересылки заказчику
- [ ] Ссылка истекает и используется только один раз; её получатель остаётся
  `pending`, пока мастер явно не подтвердит показанный Telegram-аккаунт
- [ ] Приглашённый пользователь без ручного SQL задаёт таймзону и расписание,
  проверяет права и доходит до готового `dry-run`
- [ ] Незавершённый onboarding не создаёт отложенных ответов и dry-run карточек
- [ ] Мастер видит пользователя и техническое состояние, но не видит его
  контакты, тексты или dry-run превью
- [ ] Отзыв доступа блокирует новые события и уже отложенные задачи не позднее
  следующего worker tick
- [ ] Повторное приглашение отозванного пользователя требует нового токена и не
  восстанавливает live автоматически
- [ ] Два владельца с одинаковым контактом имеют независимые расписания,
  исключения, шаблоны, FSM, статистику и очередь
- [ ] Все переходы ролей и onboarding покрыты тестами; попытки повышения роли и
  cross-tenant доступа отклоняются
- [ ] Живой тест: мастер приглашает отдельный аккаунт, тот подключает один
  тестовый чат и получает свою dry-run карточку

**Блокирует:** передачу бота заказчикам и любой внешний пилот.

### Этап 1.7. Наблюдение на боевом аккаунте

**Объём:** 7 календарных дней, работа — ~1 час в день
**Цель:** откалибровать классификатор и списки исключений до того, как бот получит право говорить.

**Задачи**
1. Подключить к основному аккаунту владельца, `dry_run = true`
2. В Telegram выставить область «все чаты, кроме исключений»
3. Занести стартовые исключения: близкие, активные рабочие переписки
4. Владелец ежедневно размечает превью кнопками
5. Раз в 2–3 дня — разбор ошибок, правка промпта, словаря, порога, шаблонов

**DoD**
- [ ] Минимум 7 дней в dry-run на реальном потоке
- [ ] Не менее 30 размеченных превью в `shadow_feedback`
- [ ] Доля вердикта `ok` — не ниже 90%
- [ ] Ни одного случая, когда бот собирался ответить исключённому контакту
- [ ] Ни одного пропуска денежного сообщения (recall по `money` = 100% на размеченной выборке)
- [ ] Тексты шаблонов финализированы и согласованы владельцем
- [ ] Список стартовых исключений финализирован
- [ ] Владелец явно подтверждает готовность к боевому режиму

**Правило:** если доля `ok` ниже 90% — неделя продлевается. Этот критерий не обходится сроками.

| Исходящие владельца не приходят в `business_message` | средняя | высокое | Этап 0 закрывает вопрос; при худшем сценарии — деградированная эвристика, согласованная с владельцем |
| Классификатор путает категории | высокая | среднее | неделя dry-run, порог уверенности, при сомнении — общий шаблон |
| Неуместный ответ важному контакту | средняя | высокое | dry-run, стартовые исключения, задержка, приоритет живого ответа, kill switch |
| Требуется Premium, которого нет | низкая | среднее | Этап 0, $5/мес |
| Telegram меняет правила Business API | низкая | высокое | вся логика Telegram-специфики изолирована в одном слое |
| Утечка личной переписки | низкая | очень высокое | тела не хранятся, в LLM — только текущее сообщение, БД без внешнего доступа |
