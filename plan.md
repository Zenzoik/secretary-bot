# Telegram Secretary Bot — Спецификация и план реализации

Версия: 1.0
Дата: 27.08.2026
Связанный документ: `ARCHITECTURE.md`

---

## Часть I. Идея

### Проблема

Владелец получает сообщения круглосуточно. Ночью и в выходные он не отвечает, но отправитель этого не знает: человек ждёт, нервничает, пишет повторно. Отдельная категория — сообщения про деньги: их владелец хочет видеть первыми, а отправителю важно понимать, что вопрос не потерялся.

### Решение

Бот, подключённый к личному аккаунту через Telegram Secretary Mode. В нерабочее время он отвечает от имени владельца одним коротким сообщением, а денежные вопросы дополнительно кладёт в утренний список владельца.

Получатель видит обычное сообщение от владельца — без пометки о боте. Поэтому текст должен быть честным, а бот в переписку не вступает: одно сообщение и молчание.

### Чего решение НЕ делает

- Не ведёт диалог вместо человека
- Не работает в группах (платформа не позволяет)
- Не пишет первым (окно 24 часа)
- Не заменяет владельца в решении вопросов — только снимает тревогу ожидания

## Часть II. Спецификация

### 2.1 Функциональные требования

**FR-1. Подключение**
Бот подключается к аккаунту владельца через Secretary Mode. Обрабатывает установку, изменение прав и разрыв соединения.

**FR-2. Область действия**
Политика «все чаты, кроме исключений». Новый контакт автоматически попадает под действие бота.

**FR-3. Расписание**
Владелец задаёт quiet-окна: дни недели + интервал времени + таймзона. Бот отвечает только внутри окна. Окна через полночь поддерживаются.

**FR-4. Исключения**
Контакт можно исключить навсегда или до конца дня. Жёстко исключены всегда: боты, сервисные аккаунты, сообщения самого владельца.

**FR-5. Два сценария ответа**

| Условие | Шаблон |
|---|---|
| Обычное сообщение | «Сейчас нерабочее время, отвечу позже» |
| Денежная тематика | «Отвечу первым делом утром» |

Тексты редактируются владельцем.

**FR-6. Классификация**
LLM определяет категорию сообщения. При недоступности LLM — fallback на словарь ключевых слов. При уверенности ниже порога — общий шаблон.

**FR-7. Один ответ на окно**
Сколько бы сообщений контакт ни прислал за одно quiet-окно, автоответ уходит один раз.

**FR-8. Задержка**
Ответ отправляется через 60–240 секунд после входящего (случайно).

**FR-9. Приоритет живого человека**
Если владелец ответил в чат сам до истечения задержки — автоответ отменяется.

**FR-10. Утренний список**
Денежные сообщения попадают в список, который владелец получает в 08:00: кто, во сколько, о чём одной строкой.

**FR-11. Dry run**
Режим, в котором бот ничего не отправляет контактам, а показывает владельцу предполагаемый ответ с кнопками оценки.

**FR-12. Управление**
Команды в личке бота: `/status`, `/off`, `/on`, `/mute`, `/today`, `/live`.
Deep-link «Manage Bot» из любого управляемого чата открывает карточку контакта с быстрыми действиями.

**FR-13. Лог**
Все решения бота записываются: контакт, время, действие, категория, шаблон. Без тел сообщений.

### 2.2 Нефункциональные требования

| ID | Требование |
|---|---|
| NFR-1 | Ответ на webhook Telegram — менее 200 мс, вся работа асинхронно |
| NFR-2 | Тела сообщений в MVP не сохраняются нигде |
| NFR-3 | В LLM уходит только текущее сообщение, без истории и имён |
| NFR-4 | Kill switch срабатывает в два тапа с телефона |
| NFR-5 | Ошибка LLM или БД никогда не приводит к отправке неверного сообщения — при сбое бот молчит |
| NFR-6 | Дедупликация входящих: повторная доставка апдейта не даёт второго ответа |
| NFR-7 | Схема БД мультиарендная, всё привязано к `connection_id` |

### 2.3 Принцип по умолчанию

**При любой неопределённости бот молчит.** Пропущенный автоответ — незаметен. Неуместный автоответ важному человеку в 3 часа ночи — репутационный ущерб и потеря доверия к системе.

### Этап 0. PoC и снятие неизвестных

**Объём:** 0.5 дня
**Цель:** подтвердить, что платформа даёт то, на чём построена архитектура.

**Задачи**
1. Создать бота, включить Secretary Mode в @BotFather
2. Поднять webhook с `secret_token`, поймать апдейт `business_connection`
3. Подключить бота к тестовому аккаунту, залогировать содержимое `rights`
4. Ответить эхом на входящее через `send_message(business_connection_id=...)`
5. **Проверить: требуется ли Premium** на аккаунте владельца
6. **Проверить: приходят ли исходящие самого владельца** как `business_message`
7. Проверить поведение при истёкшем окне: воспроизвести `BUSINESS_CHAT_INACTIVE`

**DoD**
- [ ] Бот подключается к аккаунту, соединение видно в логах
- [ ] Эхо-ответ доходит до контакта от имени владельца, без пометки бота
- [ ] Письменно зафиксировано: нужен Premium — да/нет
- [ ] Письменно зафиксировано: исходящие владельца приходят — да/нет
- [ ] Структура `BusinessConnection.rights` задокументирована в репозитории
- [ ] Если исходящие НЕ приходят — с владельцем согласована деградированная логика FR-9

**Блокирует:** всё остальное. Пока пункт не закрыт, дальше не идём.

### Этап 1. Ядро

**Объём:** 3 дня
**Цель:** работающая логика автоответчика с включённым dry-run.

**Задачи**
1. Схема БД + Alembic-миграции по `ARCHITECTURE.md` §7
2. Ingest: валидация, дедуп в Redis, постановка в очередь
3. Hard filter (§6.1)
4. Gate: расписание, исключения, лимит «один ответ на окно» (§6.2)
5. Классификатор: промпт, парсинг JSON, таймаут, словарный fallback, порог уверенности
6. Отложенная задача с рандомной задержкой
7. Проверка «владелец ответил сам»
8. Отправка + обработка ошибок Telegram (§6.5)
9. Dry-run: превью владельцу с кнопками, запись в `shadow_feedback`
10. Money-флаг → `morning_queue`, доставка в 08:00
11. Логирование всех решений
12. Docker Compose, деплой на VPS

**DoD**
- [ ] Входящее в quiet-окно порождает ровно одну запись в `message_log`
- [ ] Пять сообщений подряд от одного контакта дают **один** автоответ
- [ ] Сообщение вне quiet-окна: `action = skipped_schedule`, отправки нет
- [ ] Исключённый контакт: `action = skipped_excluded`
- [ ] Сообщение от бота или от 777000 не доходит даже до gate
- [ ] Ответ владельца в чат до истечения задержки отменяет автоответ (`skipped_owner_replied`)
- [ ] Отключённый LLM (заглушка с ошибкой) → срабатывает словарный fallback, бот не падает
- [ ] Пустой ответ LLM / невалидный JSON → категория `general`, бот не падает
- [ ] `confidence` ниже порога → `general`
- [ ] `dry_run = true`: превью приходит владельцу, контакту **ничего не уходит** — проверено на реальном чате
- [ ] Денежное сообщение создаёт запись в `morning_queue`, в 08:00 приходит список
- [ ] `BUSINESS_CHAT_INACTIVE` не вызывает ретраев
- [ ] `FLOOD_WAIT` обрабатывается с отложенным ретраем
- [ ] Тела сообщений отсутствуют в БД — проверено запросом по всем таблицам
- [ ] Сервис переживает рестарт контейнера без потери отложенных задач
- [ ] Юнит-тесты на gate и классификатор, покрытие ветвлений gate — 100%

### Этап 1.5. Control plane

**Объём:** 0.5 дня
**Цель:** владелец управляет ботом с телефона, не заходя никуда.

**Задачи**
1. Команды `/status`, `/off`, `/on`, `/mute`, `/today`, `/live`
2. Разбор диплинка `/start bizChat<user_chat_id>`
3. Карточка контакта с кнопками: исключить навсегда / не трогать сегодня / свой шаблон
4. Подтверждение на `/live` отдельной кнопкой

**DoD**
- [ ] `/off` останавливает отправку немедленно, `/status` это отражает
- [ ] `/on` возвращает работу
- [ ] `/mute 3` останавливает на 3 часа, потом работа возобновляется сама
- [ ] Кнопка «Manage Bot» в реальном чате открывает карточку **этого** контакта
- [ ] «Исключить навсегда» из карточки создаёт запись в `exclusions`, следующее сообщение от контакта не обрабатывается
- [ ] «Не трогать сегодня» ставит `until` на конец суток в таймзоне владельца
- [ ] `/live` без подтверждения не переключает режим
- [ ] `/today` показывает список действий за сутки

### Этап 1.6. Наблюдение на боевом аккаунте

**Объём:** 7 календарных дней, работа — ~1 час в день
**Цель:** откалибровать классификатор и списки исключений до того, как бот получит право говорить.

**Задачи**
1. Подключить к основному аккаунту владельца, `dry_run = true`
2. В Telegram выставить область «все чаты, кроме исключений»
3. Занести стартовые исключения: близкие, активные рабочие переписки
4. Владелец ежедневно размечает превью кнопками
5. Раз в 2–3 дня — разбор ошибок, правка промпта, словаря, порога, шаблонов

**DoD**
- [ ] Минимум 7 дней в dry-run на реальном потоке
- [ ] Не менее 30 размеченных превью в `shadow_feedback`
- [ ] Доля вердикта `ok` — не ниже 90%
- [ ] Ни одного случая, когда бот собирался ответить исключённому контакту
- [ ] Ни одного пропуска денежного сообщения (recall по `money` = 100% на размеченной выборке)
- [ ] Тексты шаблонов финализированы и согласованы владельцем
- [ ] Список стартовых исключений финализирован
- [ ] Владелец явно подтверждает готовность к боевому режиму

**Правило:** если доля `ok` ниже 90% — неделя продлевается. Этот критерий не обходится сроками.

**Объём:** 0.5 дня + неделя присмотра
**Цель:** бот отвечает по-настоящему.

**Задачи**

- [ ] Ни одного дубля автоответа
- [ ] Алерт при `BUSINESS_CONNECTION_INVALID` проверен вручную (разрыв соединения в настройках)
- [ ] Короткий runbook: что делать при сбое, как быстро всё выключить

### Этап 3. Mini App

**Объём:** 2–3 дня
**Цель:** настройка без разработчика.

Делается **после** недели боевой эксплуатации: к этому моменту половина требований к интерфейсу изменится.

**Задачи**

4. Веб-версия на том же коде

**DoD**
- [ ] Владелец меняет расписание из приложения, изменение применяется без рестарта
- [ ] Шаблоны и промпт классификатора редактируются из UI, не из кода
- [ ] Исключения добавляются и снимаются из UI
- [ ] Лог за 30 дней с фильтром по контакту и действию
- [ ] Попытка обращения к API с чужим `initData` отклоняется
- [ ] Владелец самостоятельно, без разработчика, выполняет полный сценарий настройки

### Этап 4. Дайджест

**Объём:** 2–3 дня
**Статус:** после MVP, по решению владельца.

**Задачи**
1. Включить хранение тел сообщений: `body_encrypted` (AES-GCM) + `retention_until`
2. Задача очистки просроченных записей
3. Сборка периода → LLM → 3–5 пунктов
4. Доставка владельцу по расписанию

**DoD**
- [ ] Тела сообщений хранятся в зашифрованном виде, ключ вне БД
- [ ] Записи старше TTL удаляются автоматически, проверено
- [ ] Дайджест за сутки приходит по расписанию
- [ ] Дайджест содержит только то, что реально было — сверено вручную с логом за 3 дня
- [ ] Хранение можно отключить одним флагом, бот продолжает работать без дайджеста

## Часть IV. Риски

| Риск | Вероятность | Влияние | Что делаем |
|---|---|---|---|
| Исходящие владельца не приходят в `business_message` | средняя | высокое | Этап 0 закрывает вопрос; при худшем сценарии — деградированная эвристика, согласованная с владельцем |
| Классификатор путает категории | высокая | среднее | неделя dry-run, порог уверенности, при сомнении — общий шаблон |
| Неуместный ответ важному контакту | средняя | высокое | dry-run, стартовые исключения, задержка, приоритет живого ответа, kill switch |
| Требуется Premium, которого нет | низкая | среднее | Этап 0, $5/мес |
| Telegram меняет правила Business API | низкая | высокое | вся логика Telegram-специфики изолирована в одном слое |
| Утечка личной переписки | низкая | очень высокое | тела не хранятся, в LLM — только текущее сообщение, БД без внешнего доступа |
