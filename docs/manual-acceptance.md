Актуализировано: 06.09.2026. Бот: `@perssecretbot`. Тестовый контакт:
`@poldotk` (второй аккаунт), канал: `test secretary`.

Это основной файл сценариев и результатов ручной проверки. Источники:
[реестр готовности](rollout-readiness.md), [первый аудит](audit-2026-09-05.md),
[проверка аудита](audit-verification-2026-09-05.md). Старые результаты в

«Пройден» означает подтверждение владельцем/скриншотом или проверкой живого
журнала. Автотесты сами по себе не закрывают ручной сценарий. «Частично» означает,
что конкретный остаток указан ниже. Текущий rollout ещё не принят полностью.

## Подготовка и правила проверки

1. Использовать только выбранные тестовые чаты. Перед сценарием сверить `/status`
   и Mini App: режим, паузу, часовой пояс, персональное расписание и исключение.
2. По умолчанию `/dryrun`: превью получает владелец, контакт ничего не получает.
   Для автоответа в live отдельно включить «Увімкнути відповіді клієнтам» и
   подтвердить; после сценария вернуть `/dryrun`.
3. Ручной ответ и подтверждение платного обращения — реальные действия даже
   при dry-run. Тестовые начисления сохраняются в отчёте. Отказ владельца
   в текущей реализации не отменяет начисление.
4. Для сценариев во время задержки установить 60–60 секунд. После входящего
   выполнить действие через 10 секунд; итог проверять после 70 секунд.
5. Время устройства Europe/Prague и расписания Europe/Kyiv различается.
   В журнале ниже техническое время — UTC. Ожидаемые часы проверять в явно
   указанном часовом поясе.
6. Перед диагностикой разработчик проверяет `/readyz`, актуальный webhook,
   очередь обновлений и журнал конкретного тестового сообщения. При сбое
   сначала зафиксировать результат, затем повторять сценарий.

  клавиатуры, пока бот не отправит новую.

  При потере права `deactivate_connection` намеренно включает общий стоп

  наше: у поля нет ни `min`, ни `max`, ни `required`, наши ошибки выводятся

  начинать период, который заканчивается меньше чем через `SUMMARY_PERIOD`
  после последнего доставленного, либо иначе закрепить границы уже
  выпущенных суток. Затрагивает M33–M38, где дубли выпусков проверяются
  отдельно.
- M20: повторный ответ на уже обработанный запрос игнорируется молча — дубль
  не отправляется (требование выполнено), но владелец не получает никакого
  ответа и не понимает, что запрос уже закрыт. Решить, нужна ли короткая

- 06.09.2026 обнаружена активная ошибка дневного саммари («Підсумки»,
  connection_id=2, период 2026-09-05 14:53 — 2026-09-06 14:53 UTC, run_id=4):
  каждые ~60–70 секунд (первые попытки зафиксированы в 17:49:50, 17:50:59,

  сообщений): модель `gpt-5-mini` тратит весь лимит `SUMMARY_OUTPUT_TOKENS=1024`

  `incomplete_details.reason=max_output_tokens`, `reasoning_tokens=1024`) и
  не успевает выдать текст ответа — `response.output_text` пустой →
  `ValueError` (`llm.py:117`) → `SummaryError` (`summary.py:113`). Ошибка
  детерминированная для этого диалога и будет повторяться без изменений до
  автоматического `ABANDONED` через 3 дня (`SUMMARY_ABANDON_AFTER`); каждая
  попытка — лишний платный вызов OpenAI. Журнал (`daily_summary.py:116-120`)
  сохранял только имя класса исключения, а не `str(exc)`, поэтому причина
  была не видна без ручного воспроизведения. Исправлено 06.09.2026:
  `SUMMARY_OUTPUT_TOKENS` поднят с 1024 до 8192; пустой ответ OpenAI теперь
  называет `status` и `incomplete_details.reason`; `daily_summary` и
  `summarize_dialogue` сохраняют текст ошибки, а не только тип. Добавлен тест
  на исчерпание бюджета токенов. Замеры на том же транскрипте: при лимите 8192
  ответ завершается (reasoning ~2900 токенов). Затрагивает сценарии M33–M40

  выпуск доходит на длинном диалоге, а не только на коротком тестовом.

- Вернуть согласованный режим и расписания; убрать только временные настройки
  тестового контакта. Не считать `/dryrun` отменой уже созданных начислений.

  прежде чем использовать отчёт для реального расчёта. Автоматически не удалять.
- Настроить стабильный HTTPS-адрес и управляемый запуск: текущий Quick Tunnel
  уже терял доступность и подходит только для стенда.
- Закрыть оставшиеся сценарии либо явно записать принятые ограничения.
  Не объявлять полный rollout завершённым по результатам одного дня.

## Как записывать следующий результат

Для каждого сценария: дата/время и пояс, версия или коммит, выполненные шаги,
режим и настройки, ожидаемый/фактический результат, ссылка на скриншот или
идентификатор тестового события, статус и найденный дефект. Отсутствие ответа
не считается успешным результатом, пока не проверена причина в журнале.
