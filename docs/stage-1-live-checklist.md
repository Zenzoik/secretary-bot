# Этап 1 — проверка на живом Telegram

Проверка выполняется только с одним контролируемым контактом и при
`connections.dry_run = true`. Между сценариями разработчик очищает claim
quiet-окна только для тестового контакта и сверяет обезличенные записи в БД.

## 0. Безопасное начальное состояние

1. В Telegram открыть `Settings → Chat Automation`.
2. Убедиться, что выбран режим `Only Selected Chats` и добавлен только тестовый
   контакт.
3. Не включать live-режим и не расширять список доступных чатов.
4. Разработчик проверяет: Compose healthy, публичный `/healthz` отвечает,
   webhook указывает на текущий HTTPS URL, `pending_updates = 0`,
   `last_error = null`.
5. Разработчик проверяет в БД: соединение активно, `dry_run = true`,
   `kill_switch = false`, текущее время входит в тестовое quiet-окно.

## 1. Базовый dry-run

1. Тестовый контакт отправляет: `Привет, ответишь позже?`
2. Подождать до 4 минут — задержка выбирается из диапазона 60–240 секунд.
3. Владельцу должна прийти одна карточка предполагаемого ответа с кнопками.
4. Тестовый контакт не должен получить автоматического сообщения.
5. Нажать `✅ Норм`.
6. Разработчик проверяет одну запись `dry_run` в `message_log` и одну запись
   `ok` в `shadow_feedback`, затем готовит контакт к следующему сценарию.

## 2. Один ответ на quiet-окно

1. После подтверждения разработчика тестовый контакт отправляет пять сообщений
   подряд с интервалом 1–2 секунды.
2. Подождать до 4 минут.
3. Владельцу должна прийти ровно одна карточка, контакту — ни одного автоответа.
4. Разработчик проверяет: одна запись `dry_run` и четыре
   `skipped_window_limit`.

## 3. Приоритет ручного ответа владельца

1. После подтверждения разработчика тестовый контакт отправляет одно сообщение.
2. Владелец отвечает этому контакту вручную в течение 30 секунд.
3. Подождать 4 минуты.
4. Карточка dry-run для этого входящего не должна прийти.
5. Разработчик проверяет `skipped_owner_replied` и отсутствие отправки ботом.

## 4. Исключённый контакт

1. Разработчик временно добавляет тестовый контакт в `exclusions`.
2. Контакт отправляет одно сообщение.
3. Карточка и автоответ не должны прийти.
4. Разработчик проверяет `skipped_excluded` и удаляет тестовое исключение.

## 5. Денежная категория и утренний список

1. После подтверждения разработчика контакт отправляет:
   `Когда будет оплата по инвойсу?`
2. В dry-run карточке ожидается категория `money` и денежный шаблон.
3. Разработчик проверяет новую недоставленную запись в `morning_queue`.
4. Для проверки без ожидания следующего утра разработчик запускает один
   контролируемый tick планировщика с временем 08:00 в таймзоне владельца.
5. Владельцу должен прийти один утренний список; повторный tick не должен
   прислать его второй раз.

## 6. Восстановление отложенной задачи после рестарта

1. После подтверждения разработчика контакт отправляет одно сообщение.
2. Разработчик убеждается, что задача появилась в Redis и ещё не стала due.
3. Разработчик перезапускает только app-контейнер.
4. В течение оставшегося времени задержки владельцу должна прийти одна карточка.
5. Контакт не должен получить ничего, задача в Redis должна исчезнуть.

## 7. Истёкшее 24-часовое окно

Этот сценарий выполняется отдельно, когда в контролируемом чате не было
входящих больше 24 часов. Разработчик делает одну адресную попытку через
Business Connection, не переводя весь бот в live. Ожидается
`BUSINESS_CHAT_INACTIVE`, одна попытка и отсутствие ретраев. Если ещё есть риск,
что окно активно, текст и момент попытки заранее согласуются с владельцем.

## Что не воспроизводим вручную

- `FLOOD_WAIT` — искусственное создание лимита может затронуть аккаунт;
- сообщения от `777000` и служебных ботов;
- пустой/невалидный JSON LLM и сетевой timeout;
- низкий `confidence` классификатора.

Эти ветки проверяются автоматическими тестами. Реальный Claude-путь проверяется
отдельно после добавления `ANTHROPIC_API_KEY`; без ключа приложение намеренно
работает на словарном fallback.
