## Границы гарантий доставки

- Входящие не сохраняются открытым текстом ради повтора. До завершения обработки
  они остаются неподтверждёнными у Telegram. Telegram повторяет неуспешные webhook,
  но количество попыток ограничено, а хранение входящих на его стороне не дольше
  24 часов. Длительный простой требует проверки пропущенных чатов, а не обещания
  бесконечного восстановления. [Telegram Bot API](https://core.telegram.org/bots/api#setwebhook).
- Успешная внешняя отправка и запись результата в БД не образуют общую транзакцию.
  Если результат неизвестен, выбирается отсутствие автоматического дубля:
  `DELIVERY_UNCERTAIN`, проверка чата владельцем перед новым ручным сообщением.
- Платные уведомления доставляются с повторами. При потере ответа Telegram или
  аварии между отправкой уведомления и фиксацией результата возможно повторное
  уведомление; само платное обращение и сумма повторно не начисляются.
- Пауза/выключение не удаляют отложенные задачи: worker отказывает каждой в её
  срок и записывает `skipped_kill_switch`, поэтому отказ виден в журнале и в
  `🗓 Сьогодні`. Уже принятый Telegram сетевой запрос отменить задним числом
  невозможно.
- Ответ, восстановленный после простоя позже чем через 2 часа после входящего,
  не отправляется: запись `error/STALE_REPLY`. Запоздалый автоответ хуже пропущенного.
- Для сообщений контактам неизвестный исход никогда не повторяется автоматически.
  Для выпусков саммари в канал или личку владельца повтор выполняется после
  10-минутного cooldown, потому что дубль заголовка дешевле застрявшего выпуска;
  выпуск, не доставленный за 3 дня, закрывается как `ABANDONED` с уведомлением.
- Источником метаданных очереди является БД; Redis хранит аренды. Миграция не
  создаёт открытого хранения тел входящих или ручных ответов.

## Автоматическая проверка

```bash
uv sync --dev
uv run ruff check .
uv run python -m pytest --cov=secretary_bot --cov-report=term-missing
npm ci --ignore-scripts
npm test
node --check src/secretary_bot/web/static/app.js
```

`tests/test_postgres_redis.py` запускается отдельно только с явно заданными
`TEST_AUDIT_DATABASE_URL` и `TEST_AUDIT_REDIS_URL` для изолированного стенда.
Каждый тест создаёт/удаляет собственную схему PostgreSQL и собственный ключ Redis;
один тест намеренно завершает собственный дочерний worker через SIGKILL.
Рабочие подключения и пользовательские данные для тестов не используются.

DOM-тесты исполняют настоящий JS Mini App с тестовым API и проверяют поведение,
но не заменяют рендеринг в браузере. Browser runtime в этой сессии вернул пустой
список доступных браузеров; визуальная проверка не помечена выполненной.

## Контролируемый тест и rollout

1. Подготовить резервную копию PostgreSQL и проверить её восстановление на
   отдельной БД. Сохранить ключ шифрования отдельно от БД. Не выводить секреты
   в журнал выполнения.
2. На тестовом окружении остановить старый app, применить миграции до
   `20260905_0024`, запустить новую версию. Не держать старый и новый consumer
   одновременно: формат claims/dedup изменился.
3. Проверить `/readyz` (workers, PostgreSQL, Redis). `/healthz` остаётся проверкой
   процесса; Docker использует readiness. Grace period контейнера — 45 секунд;
   таймаут прокси webhook должен позволять 30-секундный бюджет обработки.
4. Подключить отдельный тестовый аккаунт, оставить Only Selected Chats и dry-run.
   Проверить сценарии живой приёмки ниже. Текущая работа не меняла настройки
   рабочего бота и не рассылала сообщения реальным контактам.
5. Выполнить прежние критерии пилота: 7 дней dry-run, минимум 30 оценок, ≥90% `ok`,
   отсутствие неверных ответов исключённым и пропусков денежных обращений на
   размеченной выборке. Три дня сверять саммари с перепиской.
6. После приёмки включить live с подтверждением владельца, сначала для выбранных
   чатов. Наблюдать ошибки, неизвестные доставки и ожидающие уведомления.
   Расширение области — отдельное действие владельца в Telegram.

Откат поведения: `⛔ Вимкнути` останавливает автоматические ответы;
`🧪 Лише тестові прев’ю` возвращает тестовый режим. Для отката приложения
остановить новый процесс и развернуть предыдущую версию только после проверки
совместимости очереди/схемы. Миграция 0023 намеренно не выполняет слепой downgrade:
после появления одинаковых message_id в разных чатах старая уникальность уже
может быть невосстановима. При полном откате используется проверенная резервная
копия и контролируемое восстановление очередей.

## Живая приёмка: требуется перед production rollout

Эти проверки требуют Telegram/устройств и реального владельца. Они **не закрыты**
автоматическими тестами и остаются условием rollout, а не скрытым остатком кода.

- [ ] Новый владелец проходит invite → подключение → расписание → dry-run без подсказок разработчика.
- [ ] Mini App: 320/390px, desktop, светлая/тёмная тема, крупный шрифт, клавиатура; нет нечитаемых полей и перекрытых действий.
- [ ] Пауза в чате → возврат в панель; исключение во время задержки → отсутствие ответа; live → dry-run.
- [ ] Платное подтверждение, доставка обеих карточек, отказ и повторный callback без повторного начисления.
- [ ] Ручной ответ, истёкший 24-часовой чат, осознанная проверка неизвестного результата перед повтором.
- [ ] PDF из Telegram скачивается и не открывает панель без отдельного входа.
- [ ] Саммари в выбранном канале, Resolve/read-all/переход/ответ; выключение хранения; утренний список без хранения.
- [ ] 7-дневный пилот и 3-дневная сверка саммари завершены с записанными результатами.
