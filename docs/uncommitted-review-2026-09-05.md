## Подтверждённые остатки

### R1 · P1 · Задачи из БД восстанавливаются только при запуске worker

Источник: `src/secretary_bot/workers.py:85–100`.
Связь: A1/P1.3–4, A2/P1.3–4.

После первого восстановления `restored=True` исключает дальнейшее чтение
`ReplyJob`. Если во время работы Redis потерял запись, либо постановка в Redis
после коммита БД не удалась и Telegram больше не повторил update, задача остаётся
незавершённой в БД, но worker её не подхватит. Сам процесс и readiness при этом
могут оставаться исправными. Поздний ручной перезапуск может восстановить задачу
уже после двухчасового лимита, когда она будет отклонена как `STALE_REPLY`.

Воспроизведение: старт worker с пустой БД → создание настоящего ReplyJob через
pipeline → имитация потери записи очереди → ещё два прохода worker. В БД задача
есть и не завершена; в очереди по-прежнему пусто. Это моделирование потери записи,
а не утверждение о реальном сбое рабочего Redis.

Нужно периодическое согласование БД и очереди или отдельный publisher outbox.
Повторная публикация должна сохранять действующие аренды и номера попыток.

### R2 · P1 · Окончательный сбой платного уведомления невидим владельцу

Источники: `src/secretary_bot/outbox.py:57–62`, `src/secretary_bot/status.py:51–91`.
Связь: A1/P1.2 и P2.1, A2/P1.2.

После 24 неудач NotificationJob получает `completed_at`. Счётчик pending
перестаёт его учитывать. Однако `last_error` читается только из MessageLog,
куда outbox не пишет. Владелец видит «Остання помилка: немає» и ноль ожидающих
сообщений, хотя уведомление о платном обращении так и не доставлено. Комментарий
в outbox и реестр обещают видимую ошибку, которой нет.

Воспроизведено через настоящий `operating_status` с завершённым ошибкой
NotificationJob: `pending_notifications=0`, `last_error=None`.
Нужно отдельное видимое состояние недоставленных уведомлений с контактом,
обращением и способом повторить доставку без повторного начисления.

### R3 · P2 · Проверка правила расходится с реальной отправкой

Источники: `src/secretary_bot/web_api.py:310–335`,
`src/secretary_bot/web/static/app.js:529–533`.
Связь: A1/P2.8.

Подтверждены три случая:

- При `can_reply=False` и разрешающем персональном правиле API возвращает
  `decision=allowed`; реальный pipeline проверяет право ответа и отказывает.
- Для `force_template=money_priority` превью общего сообщения показывает обычный
  шаблон; pipeline выбирает принудительный шаблон контакта.
- После изменения исключения/расписания в форме проверка отправляет только
  `text` и `contact_id`. Несохранённое правило игнорируется без предупреждения,
  и пользователь может принять ответ о старой конфигурации за проверку новой.

Первые два случая воспроизведены через API; третий — на настоящем app.js в jsdom.
Различие между словарной и LLM-классификацией уже явно подписано и само по себе
не является дефектом. Нужен общий выбор правил/шаблона с pipeline и явная
семантика проверки черновика либо только сохранённых настроек.

### R4 · P2 · Отмена правок ломает карточку после поиска

Источники: `src/secretary_bot/web/static/app.js:121–125,379–384`.
Связь: A1/P2.2, A2/P2.2.

Сценарий: выбрать контакт 100 → изменить исключение → поиск, оставляющий только
контакт 101 → «Скасувати зміни». Отмена повторно ищет контакт 100 в текущем
отфильтрованном списке, присваивает `selectedContact=undefined` и выходит.
Поля остаются изменёнными, dirty становится false, дальнейшее сохранение молча
возвращается без запроса. Воспроизведено в jsdom: изменённое значение осталось,
PUT-запросов после сохранения — 0.

Нужно хранить выбранную карточку независимо от результатов поиска и восстанавливать
её из сохранённого снимка либо отдельного GET контакта.

### R5 · P2 · Светлая тема исправлена не для всех элементов

Источники: `src/secretary_bot/web/static/styles.css:48,84,272–284`.
Связь: A1/P2.9, A2/light.

У label остался фиксированный светлый `#c9d1dc`, тогда как светлая панель имеет
белый фон: расчётный контраст 1.54:1. У connection-pill/badge осталась тёмная
полупрозрачная подложка, но цвет текста в светлой теме становится тёмным
`--muted`. Тематические переменные полей исправлены, эти элементы — нет.

Существующий тест проверяет только `dataset.theme`, а не читаемость. Здесь
подтверждены CSS-значения и расчёт контраста; новая визуальная проверка в браузере
в рамках этого ревью не выполнялась. Нужно завершить перевод цветов на переменные
и проверить обе темы визуально.

### R6 · P2 · Предупреждение о реальной отправке добавлено только в один путь

Источники: `src/secretary_bot/summary_actions.py:260–268,359–365`.
Связь: A1/FR-22 и A2/FR-22.

Прямой выбор контакта предупреждает, что ответ уйдёт немедленно даже в тестовом
режиме. Кнопка ответа из карточки саммари создаёт другой ForceReply с прежним
текстом «Напишіть відповідь…»; предупреждение о dry-run отсутствует. Оба пути
используют один обработчик реальной отправки. Таким образом, обещание реестра
и пользовательской инструкции про предупреждение в запросе выполнено не везде.

Нужно одинаковое предупреждение для обоих адресных запросов; отдельное второе
подтверждение не требуется принятой механикой FR-22.

### R7 · P2 · Пересохранение даты всё ещё сдвигает повторяющийся осенний час

Источники: `src/secretary_bot/web/static/ui-utils.js`,
`src/secretary_bot/web/static/app.js:393` и обработчик сохранения контакта.
Связь: A1/P1.5, A2/P1.5.

Реальное воспроизведение Node с `TZ=Europe/Prague`:

```text
Сохранено:      2026-10-25T01:30:00.000Z
datetime-local: 2026-10-25T02:30
Пересохранено:  2026-10-25T00:30:00.000Z
```

При возврате на зимнее время локальный час повторяется. Поле теряет исходное
смещение, а Date выбирает первое вхождение. Обычный сдвиг UTC исправлен, но
условие round-trip для переходов времени из аудита выполнено не полностью.
Существующий тест проверяет обычные зимние/летние даты и весеннюю дату вне
неоднозначного интервала. Нужно сохранять исходный instant при неизменённом поле
и определить явное поведение для ввода неоднозначной даты.
