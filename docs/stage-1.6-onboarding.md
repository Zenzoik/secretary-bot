# Этап 1.6 — закрытый onboarding заказчиков

Дата автоматической проверки: 28.08.2026.

## Роли и безопасность

В системе один мастер. Его числовой Telegram ID задаётся только через
`MASTER_TELEGRAM_USER_ID`. Назначить или заменить мастера сообщением боту
невозможно; запуск с другим master ID при уже существующем мастере завершается
ошибкой.

Остальные владельцы имеют один из статусов:

- `pending` — invite погашен, мастер ещё не подтвердил аккаунт;
- `active` — доступ разрешён; до окончания onboarding pipeline заблокирован;
- `revoked` — доступ отозван, сообщения и команды не обрабатываются.

Invite-токен криптографически случайный, действует 24 часа, используется один
раз и хранится в PostgreSQL только как SHA-256. Username не участвует в
авторизации — решения привязаны к неизменяемому Telegram `user_id`.

## Сценарий мастера

1. Открыть личный диалог с ботом и нажать `➕ Пригласить`.
2. Переслать полученную ссылку конкретному заказчику.
3. После уведомления о новом запросе нажать `👥 Пользователи`.
4. Сверить показанный аккаунт и нажать зелёную кнопку подтверждения либо
   красную кнопку отказа.
5. Для остановки активного пользователя снова открыть список и нажать
   `⛔ Отозвать`.

Список содержит только идентичность, статус и шаг onboarding. Контакты,
сообщения, превью и пользовательская статистика мастеру не показываются.

## Сценарий приглашённого владельца

1. Открыть invite-ссылку. До approve доступны только ответы о статусе запроса.
2. После approve подключить бота в `Settings → Chat Automation`.
3. Выдать `can_reply` и `can_read_messages`. Без обоих прав FSM дальше не идёт.
4. Выбрать часовой пояс: Kyiv, Prague, Warsaw или UTC.
5. Выбрать один preset:
   - каждый день 22:00–08:00;
   - будни 18:00–09:00;
   - тестовый каждый день 00:00–23:59.
6. В Telegram включить `Only Selected Chats` и добавить один тестовый контакт.
7. Подтвердить область кнопкой. Только после этого снимается onboarding kill
   switch и появляется обычная панель управления.

Финальное состояние всегда `dry_run=true`, без mute и незавершённого live.
Переход в live остаётся отдельным ручным действием с пятиминутным
подтверждением.

## Отзыв доступа

При revoke в одной транзакции сохраняются `dry_run=true`, `kill_switch=true`,
сбрасываются mute/live/FSM. После commit все ожидающие задачи connection
удаляются из Redis. Если worker уже успел извлечь задачу, повторная проверка kill
switch перед отправкой всё равно её остановит.

Повторный доступ начинается с новой invite-ссылки и нового approve. Старые
настройки не могут автоматически вернуть пользователя в live.

## Что проверено автоматически

- неизвестный, pending и revoked пользователь не проходит fail-closed gate;
- второй master bootstrap отклоняется;
- invite истекает, погашается атомарно и не хранится открытым текстом;
- approve/revoke недоступны обычному пользователю;
- onboarding FSM сохраняется между обработчиками и поддерживает возврат назад;
- отсутствие чтения или права ответа блокирует настройку;
- до шага `ready` Business Messages не создают логи и задачи;
- два владельца с одинаковым contact ID полностью изолированы;
- revoke удаляет только задачи отозванного connection;
- feedback чужого владельца отклоняется.

## Живая проверка

- [ ] У мастера появились `👥 Пользователи` и `➕ Пригласить`.
- [ ] Invite открылся на отдельном Telegram-аккаунте и создал `pending`.
- [ ] Approve доставил инструкцию приглашённому владельцу.
- [ ] Business Connection с обоими правами открыл выбор таймзоны.
- [ ] После расписания и подтверждения области показан статус dry-run.
- [ ] Сообщение единственного тестового контакта создало карточку только его
  владельцу.
- [ ] Revoke удалил доступ и ожидающие задачи, не изменив состояние мастера.
