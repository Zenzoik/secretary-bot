# Этап 4 — зашифрованное хранение и суточное саммари

Дата реализации: 02.09.2026

## Согласие и границы

Владелец проекта письменно подтвердил:

> Подтверждаю хранение текстов сообщений в зашифрованном виде на срок до 48
> часов для формирования суточного саммари.

Хранение включается отдельно для каждого Business Connection и по умолчанию
выключено. Сохраняется только текст доступных приватных диалогов. Медиа, файлы,
группы, служебные сообщения и исключённые контакты не сохраняются.

## Поток данных

1. При включённом флаге pipeline шифрует входящие тексты, ручные ответы владельца
   и действительно отправленные автоответы.
2. Используется AES-256-GCM со случайным 96-битным nonce. В authenticated data
   входят connection, contact, Telegram message ID и направление; перенос
   ciphertext в другую строку обнаруживается.
3. Ключ `MESSAGE_ENCRYPTION_KEY` существует только в окружении приложения и не
   записывается в PostgreSQL.
4. Ciphertext получает `retention_until = occurred_at + 48h`. Каждые 10 минут
   worker удаляет просроченные записи пачками до 1000 строк.
5. Выключение флага через Mini App удаляет все временные тексты этого подключения
   в той же транзакции. Технический журнал и работа автоответов сохраняются.
6. В Redis попадают только прежние идентификаторы отложенной задачи и код
   шаблона — тексты туда не передаются.

## Формирование саммари

В настроенное локальное время берётся полуинтервал предыдущих 24 часов. Строки
расшифровываются только в памяти и группируются по контакту. Для каждого диалога
LLM получает хронологический transcript с ролями `IN`/`OUT`, но без имени и
Telegram ID контакта.
При использовании OpenAI запрос отправляется через Responses API с
`store=false`; модель по умолчанию — `gpt-5-mini`. Для обработки целого диалога
используется отдельный `SUMMARY_TIMEOUT_SECONDS` (по умолчанию 60 секунд), не
короткий timeout классификации одного сообщения.

Строгий JSON содержит:

- тему на украинском в 2–3 словах;
- только явно подтверждённые договорённости;
- вопросы и просьбы контакта без более поздней содержательной `OUT`-реплики;
- счётчики `задано / закрыто`.

Ответ с неверной схемой, противоречивыми счётчиками или темой другой длины не
публикуется. Один период имеет уникальную запись `summary_runs`; ID каждого
отправленного сообщения сохраняется, поэтому следующий тик или рестарт не
публикует завершённый выпуск повторно.

## Telegram-канал и действия

Если `summary_channel_id` задан, выпуск отправляется в канал; иначе — в личный
чат владельца. Заголовок содержит число диалогов, вопросов и денежных обращений.
Каждый диалог публикуется отдельной карточкой.

Канал подключает сам владелец из Mini App. В актуальном Telegram панель вызывает
нативный выбор канала через одноразовую подготовленную кнопку с TTL 15 минут.
Telegram может добавить бота администратором с минимальным правом публикации.
Для браузера и старых клиентов есть fallback по ссылке на пост закрытого канала
или `@username` публичного. В обоих путях сервер повторно проверяет тип чата,
администраторские права текущего владельца и право бота публиковать; произвольный
числовой ID через основной API принять нельзя. Старые запросы выбора удаляются
при создании нового, поэтому служебная таблица не растёт на каждый клик.

- `✅ Resolve` записывает `resolved_at` только если он пуст. Повторный callback
  отвечает `Уже вирішено` и не меняет состояние.
- `💬 Перейти в чат` использует официальный `https://t.me/<username>`, если у
  контакта есть публичный username. Username сохраняется из входящего update и
  фиксируется в карточке выпуска. Если его ещё нет в базе, первое нажатие
  повторно запрашивает чат у Telegram и обновляет кнопку. Если публичного
  username нет, бот явно сообщает, что прямой переход недоступен, и предлагает
  действие `Відповісти від бота`.
- `🤖 Відповісти від бота` создаёт отдельное FSM-состояние на 15 минут и
  присылает Force Reply владельцу. Отправляется только reply на этот prompt.
- `👁 Прочитати все` вызывает `read_business_message` по последнему входящему ID
  каждого уникального диалога именно этого выпуска.

После действия inline-клавиатура удаляется, а в сообщении остаётся постоянный
результат. Проверяется активный владелец и принадлежность item/run его
подключению.

Старая `morning_queue` больше не имеет отдельного worker в приложении. Денежные
контакты получают метку внутри саммари, а записи очереди отмечаются доставленными
только после успешного выпуска соответствующей карточки.

## Рост PostgreSQL

Объём ограничен временем, а не сроком жизни проекта. При неизменной нагрузке он
выходит на плато примерно в два суточных объёма текста плюс накладные расходы
AES-GCM и индексов. Панель показывает число ciphertext и их текущий размер.
PostgreSQL autovacuum переиспользует освобождённые страницы; физический файл не
обязан уменьшаться после каждого удаления, но не должен расти без ограничения
при стабильном потоке.

Ориентиры для коротких Telegram-текстов вместе с индексами:

| Сообщений в сутки | Окно 48 часов |
|---:|---:|
| 1 000 | примерно 4–8 МБ |
| 10 000 | примерно 40–80 МБ |
| 100 000 | примерно 0,4–0,8 ГБ |

## Автоматические доказательства

- AES-GCM round-trip, отсутствие plaintext, tamper и неверный AAD;
- TTL, ограниченная очистка и немедленный purge одного подключения;
- хранение выключено/ключ отсутствует — ответ всё равно отправляется;
- исключённый контакт не сохраняется;
- период ровно 24 часа, неактивный диалог не попадает в модель;
- имя и contact ID отсутствуют в LLM transcript;
- schema validation и вопрос, закрытый ответом;
- публикация один раз и продолжение после сохранённого прогресса;
- Resolve идемпотентен, reply привязан к Force Reply;
- read-all касается только items выбранного run;
- денежная очередь поглощается только после доставки.

Команды проверки:

```bash
uv run pytest
uv run ruff check .
node --check src/secretary_bot/web/static/app.js
```
